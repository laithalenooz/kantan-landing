Chapter 1 · the problem

Agents write good code. Then they mark their own homework.

You trust Claude to write the code. Trusting it to decide it's finished is a different thing. Drag the slider and see how much the agent's confidence changes the result.

The agent, reporting back
All tests pass! I'm {{conf}}% sure the importer is done.
not at allextremely
What kantan does instead 
$ npm test
  ✓ parses the manifest
  ✓ maps known fields
  ✕ warns once per dropped field
9 passing, 1 failing
exit 1 {{quip}}

The server runs your tests, not the agent. It branches on the exit code and never on the agent reporting success. You can't talk an exit code into anything.

Chapter 5 · what this is not

The opposite of an agent framework.

  • An org chart of agents
  • Autonomy nothing wakes itself up
  • Multi-agent orchestration
  • A tracker database
  • Worktree sprawl

One task. One human decision. Your tests. That's the whole thing.

One run per project.

Two agents never share a working tree. A task that can't start yet tells you why in a sentence, instead of just greying out a button.

"kantan runs one task at a time, so this one can start once that run finishes or you stop it."

Rough edges, by name

  • The usage view only sees what kantan's own runs reported.
  • A second account has to be named by hand, once.
  • src/run.ts is 2,695 lines of one state machine.
  • One 731 KB bundle, no code splitting.
  • An event a future CLI adds shows up as raw JSON until someone gives it a row. It stays visible, though.
